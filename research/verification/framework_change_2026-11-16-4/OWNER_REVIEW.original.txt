## 3. Improvements, in priority order

P0 — Make the prospective evidence independently auditable

The scorer currently evaluates contracts entered in each card without comparing them against an immutable copy of the user's original requested lines. It also reads locally mirrored GitHub push receipts.

Add an original-request manifest with contract hashes, externally verifiable first-play timestamps, and independent re-verification of push receipts. This would close important opportunities for accidental selection bias or incorrect timing evidence.

P0 — Run the first genuine prospective validation

Freeze the methodology and collect the first 100 eligible games, then continue toward the registered 400-game decision horizon. Track all requested games, including unpriced, late, unresolved and excluded games.

Compare forecasts against the pre-registered 0.5 benchmark and stronger sporting-data-only baselines. Report Brier score, log loss, calibration, coverage and uncertainty by sport and contract. No retrospective analysis should substitute for this experiment.

P1 — Build a reliable structured training dataset

The retrospective reports 5,402 learning-store events, but only 20 associated with carded games and very limited team statistics. Capture all researched L5/L10/L20 results, opponent strength, lineup status, injuries, venue, rest, and contextual adjustments in machine-readable form.

Enforce real competition/event IDs, source provenance, missingness checks, deduplication and point-in-time data availability. Prioritise dataset quality over collecting more loosely structured results.

P1 — Introduce CI and protected releases

Restore a GitHub Actions workflow that runs tests, formatting/static checks, card-schema validation and a small end-to-end evaluation fixture on every proposed change.

Protect `main` with required passing checks. Replace the current seal command's direct-to-main push dependency with a controlled, timestamped ingestion path that still permits cards to be sealed promptly before play.

P2 — Improve forecasting models only after the data and evaluation are stable

Develop sport-specific baselines with hierarchical competition effects, opponent-adjusted strengths, rest/travel and verified availability features. Use chronological backtesting, held-out competitions and prospective shadow comparisons.

Test whether ML or adaptive expert weighting genuinely improves calibrated probabilities over simpler models. Avoid promoting RL or complex ensembles solely because they fit historical results.

P2 — Simplify the documentation and operating workflow

The latest tree contains approximately 5,350 tracked entries, with large archive and verification directories. Maintain one current specification, one version registry and one concise runbook. Keep superseded designs accessible, but clearly separate them from active rules.

Reduce repeated instructions and use generated documentation where practical. This would lower the chance of different research chats applying different policies.

## Final recommendation

The next improvement should not be another major forecasting-model version. The highest-value work is to make the v26.0 experiment trustworthy, operate it consistently and collect sufficient prospective evidence.

The repository already contains substantial research rules, numerical tooling, historical records and integrity tests. Turning those components into a reliable end-to-end measurement system would provide more value than adding further prediction algorithms immediately.

The review was a static inspection of the current GitHub tree, key Python modules, tests, evaluation plan and retrospective—not a full dynamic security or performance audit. No repository files were modified.
